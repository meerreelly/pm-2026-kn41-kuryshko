резерву. Перевищити стелю після першого ж уточнення було б гірше, ніж недобрати
зараз.

## 2. Правило 100%: як перевіряли

Спосіб перевірки: кожен нелистовий вузол підсумував вручну і звірив з батьківським рядком:
1.1 = 100 = 60+40; 1.2 = 100 = 40+60; 1.3 = 820 = 180+220+120+100+80+80+40;
1.4 = 360 = 220+100+40; 1.5 = 100 = 60+40; корінь = 1480 = 100+100+820+360+100.
Потім те саме перерахував валідатор, правило `WBS-3`.

Робота, яку ледь не забули: документація і передача сервісу адміністратору ІТ-служби академії,
який супроводжує продакшн після пілота. Окремого вузла не заводив, обсяг малий
і далі не ділиться, тому вона дописана в `deliverable` пакета 1.5.2.
Друге — приймальне тестування: у першому чорновику воно лежало разом зі
звичайним. Виніс його окремим вузлом 1.4.2, бо там інша точка приймання
і демо на 25 учасників одночасно.

Що свідомо поза обсягом:

- Прямий API-імпорт історій з Jira (S-09, `wont`): залежність від чужого API для REL-1 не потрібна.
- Окремі мобільні застосунки: браузера досить.
- Таймер раунду (S-08) і довільні колоди карток (S-12, `wont`): у першому релізі фіксована шкала Фібоначчі.
- Окремі робочі простори інших кафедр: після перевірки пілота.
- Самостійне видалення сесії через UI (S-13): дані пілота видаляє адміністратор за погодженим строком.

Список збігається з розділом 3 статуту «Не робимо».

## 4. Критичний шлях

Дата старту робіт: 2026-11-02, понеділок. Тиждень це п'ять робочих днів,
свята не рахую.

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 88 |
| Ланцюг критичних робіт | T-04 → T-05 → T-06 → T-07 → T-09 → T-10 → T-13 → T-14 → T-17 |
| Дата завершення за планом | 2027-03-04 |
| Строк мого варіанта, робочих днів | 60 (12 тижнів × 5) |
| Різниця | +28 робочих днів понад строк варіанта |

Чи вкладаємось: **ні**. За строком варіанта реліз мав би вийти 2027-01-25,
критичний шлях дає 2027-03-04, тобто на 28 робочих днів пізніше.

Що з цим робимо: фіксую обсяг, рухаю дату. Історії REL-1 лишаються в релізі всі,
бо кожен із чотирьох критеріїв успіху спирається на конкретні з них; прибрати
статистику розкиду означає зірвати SC-03, і демо, заради якого проєкт існує,
не відбудеться. Прискорювати роботи з резервом (T-01, T-02, T-03) безглуздо,
вони й так ідуть паралельно і жодного дня не дають.

Ланцюг «критерії → дизайн → доступ → сесія → історія → експорт → тестування →
приймання» послідовний за змістом: сесія не почнеться без ролей доступу,
а приймальне демо не пройде, поки не протестовано все. Єдине прискорення,
яке тут було можливе, я вже заклав: на пакетах доступу і сесії обидва
розробники працюють разом, 16 годин на день замість 8. Більше розпаралелити
нема чого.

Ціна рішення: кафедра отримує пілот на півтора місяці пізніше за номінальний
строк варіанта. Розмову про це з ST-01 і ST-02 веду на ЛР13.

Робота з найбільшим резервом: T-03 «Ведення беклогу і ризиків», 78 робочих днів.
Це фонова робота PM, від неї не залежить жодна інша, тому вона може йти
будь-коли в межах проєкту.

Разом із цією роботою я проставив `REL-2` історіям S-08 і S-13. S-09 і S-12
лишились без релізу: клас `wont` означає, що в найближчі релізи вони не йдуть.

Що фіксовано в першому релізі, обсяг чи дата: **обсяг**. Історії REL-1 лишаються всі, а дата рухається
за критичним шляхом: з 2027-01-25 на 2027-03-04.

Точність дати `REL-2`: 2027-06-01 це квартальний орієнтир. Зобов'язанням вона не є
і точності тут не передбачено: горизонт завеликий.
