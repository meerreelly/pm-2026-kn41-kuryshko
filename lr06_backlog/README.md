## 2. Метод пріоритезації і чому саме він

Метод: **MoSCoW** (moscow). Маємо контекст кафедри, але не маємо виміряних
reach, impact і вартості затримки; числова RICE/WSJF зараз дала б удавану точність.
MoSCoW дозволяє обговорити мінімум та зручності з замовником. Погодження класів
із кафедрою ще не проводилося: це пропозиція для навчального портфеля.

Що метод не побачив: S-05 (should, rank 4) стоїть перед S-03 (must, rank 5),
бо перелік і вибір історії дає тестовий контекст голосуванню.
Це свідоме відхилення від сортування за класом; при скороченні S-05
мінімальне створення однієї поточної історії залишається в потоці сесії.
Так само S-14 (should) має бути реалізована раніше за експорт S-10 (must).

## 3. Звідки взялися числа

| Клас / число | Правило та джерело |
| --- | --- |
| must | Без історії немає безпечної гостьової сесії або збереження/перенесення результатів: S-11, S-01, S-02, S-03, S-16, S-07, S-10 |
| should | Важливо для цільового навчального сценарію; можливий тимчасовий ручний обхід або спрощення після погодження SC: S-04, S-05, S-06, S-14, S-15; S-13 — після REL-1 |
| could | Таймер S-08: допомагає фасилітації, не потрібний для голосування й даних |
| wont | S-09, S-12: API-імпорт та довільні колоди не входять у цей реліз |
| 7 / 12 = 58,3% must | Пораховано з історій REL-1; поріг курсу — не більше 60% |
| priority_inputs | Порожня в усіх рядках: MoSCoW не має числових складників |

Should не означає, що можна непомітно порушити критерій успіху.
Наприклад, вилучення S-15 потребує перегляду SC-03 і погодження ручного аналізу;
поточний базовий REL-1 містить її повністю. S-14 залишається залежністю S-10,
доки не погоджено інший спосіб визначення підсумку.

## 4. Перший реліз

Ємність: **12 тижнів / 2 × 20 SP = 120 SP**, шість двотижневих спринтів V08.
Це орієнтир, а не доказ того, що історії вже оцінено: votes.csv та estimates.csv
ЛР8 залишаються порожніми. Числа витрат у business case — попередня оцінка
людино-тижнів, їх не можна механічно прирівняти до story points.

REL-1 — **12 історій** у п'яти епіках: S-01…S-07, S-10, S-11, S-14…S-16.
Епік «Доступ» та поточний епік «Статистика» входять повністю; «Сесія» —
без таймера, «Інтеграції» — лише CSV, «Адміністрування» — лише створення.
Наскрізна цінність: створити сесію → приєднати групу → оцінити → обговорити
й повторити → зберегти узгоджене → побачити розкид → експортувати.

Поза релізом: S-13 (ручне видалення адміністратором як тимчасовий обхід),
S-08 (таймер), S-12 (колоди), S-09 (API). До наступного релізу їх допускаємо
після оцінки пілота та появи місткості; REL-2 зараз не вигадуємо.

Першою скорочуємо S-05 до мінімального введення ключа/назви поточної історії
без окремого менеджера списку. Якщо цього недостатньо — переносимо S-15
із погодженням зміни SC-03. S-16, прихованість голосів і цілісність експорту
не віддаємо заради дати. Після зміни релізу перерахуємо частку must і залежності.

Список — залежності плану, а не твердження, що попередні історії вже реалізовані.
S-05 може бути спрощена, але створення поточної історії обов'язково зберігається.

Схема S-10: UTF-8, кома як роздільник; у votes.csv —
story_id,round,voter,vote; у estimates.csv —
story_id,final_estimate,rounds,spread_note.
Числова шкала 0/1/2/3/5/8/13/21; знак ? можливий у проміжному раунді,
але не останньому. У votes — псевдоніми, не ПІБ; ключі історій відповідають
беклогу команди-експортера. Для пілота перевіряємо мінімум 8 історій і 3 голоси
в раунді, звичайний груповий режим допускає всі 25 голосів.
Повторні раунди й великий розкид вимагають примітки; підсумок визначає
фасилітатор, автоматичного консенсусу немає.
